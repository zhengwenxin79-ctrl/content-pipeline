# P0 安全清理与环境配置复盘

## 做了什么

- 新增 `.env.example`，集中声明 DeepSeek、GitHub、DashScope、SMTP、小红书 Cookie、数据库、每日调度等运行配置。
- 从 `启动服务.command` 和 `每日情报.command` 移除了硬编码 `DEEPSEEK_API_KEY` 和 `XHS_COOKIE`，改为读取本地 `.env`。
- 移除了 `mailer.py` 中默认 QQ 邮箱和 SMTP 授权码，缺少 `MAIL_SENDER` 或 `MAIL_PASSWD` 时直接跳过发信并输出提示。
- 修改 `/api/config`，不再把服务端 DeepSeek key 返回给前端，只返回公开产品配置。

## 为什么这么做

项目要开放给别人试用或写进简历，首先要能证明对密钥、用户数据和部署安全有基本敬畏。硬编码 API key、Cookie、SMTP 授权码会导致额度被盗用、账号风险和部署不可控；服务端 key 下发到浏览器更是高危行为。

## 优点

- 降低凭据泄露风险，适合公开仓库和对外 Demo。
- 本地、Render、服务器部署都可以复用同一套环境变量约定。
- 缺配置时不会误发邮件或静默失败。

## 代价和不足

- 首次启动多了一步：必须复制 `.env.example` 并填写 `.env`。
- 历史提交中已经出现过的密钥仍然需要在对应平台吊销和重置，代码修改不能消除历史泄露。
- 目前只处理了最直接的密钥泄露，密码哈希、权限模型和多用户隔离在后续阶段继续加强。

## 简历/项目介绍表达

> 对原型系统进行了安全基线改造：移除仓库内明文 API key、Cookie 和 SMTP 授权码，建立 `.env.example` 配置规范，并修复服务端密钥暴露接口，为公开部署和多人试用提供安全前提。

## 复盘

这一阶段的核心不是增加功能，而是把“能跑”改成“能安全给别人看”。对早期 AI 产品来说，密钥管理和环境配置常常被忽视，但它决定项目能否从个人脚本走向真实用户试用。
