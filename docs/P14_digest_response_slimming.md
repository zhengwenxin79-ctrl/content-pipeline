# P14 `/api/digest` 响应瘦身复盘

## 做了什么

- 将 `/api/digest` 默认响应改为首页 slim digest：只返回 `_radar_picks`、`_more_candidates`、推荐模式、候选统计、用户画像/订阅状态等首屏必要字段。
- 保留完整列表能力：`/api/digest?full=1` 仍可返回分类长列表，用于研究方向筛选、订阅话题筛选、点击话题后的浏览。
- 分类长列表不再无限制返回全部文章，而是按分类质量分 Top-N 截断：默认首屏每类最多 120 篇，按需完整列表每类最多 240 篇，同时返回真实全量分类计数。
- 默认 digest 不再读取文章全文 `content`，也不再预载 3000+ 篇文章的 `reading_brief_json`，避免列表接口承担单篇阅读卡片的成本。
- 首页访问不再触发全量摘要/标题补齐任务。
- 前端首页继续首屏渲染“今日必读 + 补充候选”；用户切换到方向/话题筛选时，才按需加载完整候选列表。
- 摘要轮询改为拉取 slim digest，只更新当前页面上存在的文章卡片。
- JSON 响应支持 gzip，在浏览器支持 `Accept-Encoding: gzip` 时进一步压缩传输体积。

## 为什么这样做

线上 `/api/digest` 接近 2MB，首页请求容易慢或中途断开。问题不只是“返回字段多”，还包括默认接口把分类长列表、阅读 brief、用户反馈、个性化字段一次性全部发给首页。

首页 MVP 的核心体验是让用户快速看到 3-5 篇高价值推荐，以及最多十几篇补充候选。分类长列表属于二级浏览场景，应该按需加载。

## 优点

- 首屏响应体积从“全量分类列表”收敛到“雷达精选 + 补充候选”，公网加载更稳定。
- 完整分类列表没有删除，只是延后到用户明确需要时加载，兼顾性能和原有功能。
- 默认接口不读 `content` 和 `reading_brief_json`，减少数据库 I/O、JSON 解析和 Python 内存组装成本。
- gzip 对完整列表场景也有帮助，降低弱网传输压力。

## 代价与风险

- 第一次切换到“与我方向相关”或“订阅话题”时，会有一次完整列表加载等待。
- 当前实现是“按需加载 + 每类 Top-N 截断”，还不是严格分页；如果未来需要浏览更长历史，需要进一步拆成 `/api/digest/category?name=...&limit=...&offset=...`。
- 默认首页不再触发全量摘要/标题补齐，也不再预载阅读 brief；用户点击“阅读 brief”时仍走单篇接口读取/生成。

## 后续建议

- 增加分类分页接口，只返回当前 tab 当前页文章。
- 给 `/api/digest` 加服务端短缓存，例如 60-180 秒，避免多个用户同时访问时重复组装 digest。
- 将 `_radar_picks` 的候选生成改为数据库层 Top-N 查询，进一步减少默认接口扫描范围。
- 在前端补一个“完整候选加载失败后重试”按钮。

## 简历/项目介绍写法

- “针对推荐首页 `/api/digest` 2MB 级响应和公网 40s+ 加载问题，重构为首屏 slim payload + 二级列表按需加载，并移除首页接口对全文字段的读取，将首页数据传输从全量候选列表收敛到精选推荐字段。”
- “设计 AI+X 论文雷达的信息架构：首屏只展示每日必读与补充候选，完整候选通过用户意图触发加载，降低认知负担和网络延迟。”
